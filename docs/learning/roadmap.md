# 구현하면서 배우는 로드맵

기간보다 **완료 조건**으로 진행한다. 각 단계에서 직접 설명 → 구현 → 실험 → 근거 기록 → 면접 답변 순서를 따른다. 아래 기능은 계획이며 초기 환경 구성에 포함된 완료 기능이 아니다.

모든 단계에서 [코드·명세 기준](../../CONVENTIONS.md)을 적용한다. 구현 전에 DTO·모델 필드 표를 제시하고, 구현과 함께 API·함수 주석/명세를 제공한다. HTTP API는 Swagger 실제 호출과 Bruno assertion으로 확인하며 React Native 공유 상태는 Zustand로 관리한다. Expo 모바일 앱과 도구 연동은 [연결 검증 기록](2026-11-06-mobile-tooling.md)을 기준으로 하며, 각 기능 완료 시 계약·타입·동작·실행 근거를 함께 점검한다.

| 단계 | 구현할 것 | 직접 확인할 것 | 남길 증거 |
|---|---|---|---|
| 0. 환경 | 세 서비스·Compose·Wrapper·기존 웹·Expo 모바일 | 저장소 없이 빌드·모바일 연결, Docker 설치 후 의존성 health | 초기·모바일 검증 보고서 |
| 1. 최소 도메인 | PostgreSQL 요청 저장·조회, JPA·Flyway, 데모 해석 규칙 | 같은 입력·상태 전이, 잘못된 요청, 본인 결과만 조회 | ERD·API·테스트·선택 이유 |
| 2. 비동기 MSA | 요청 이벤트 → interpretation → Mongo 결과 → 완료 이벤트 → fortune 상태 갱신 | 소비자 정지 중 접수, 재시작 후 처리, 처리 지연 상태 표시 | 시퀀스 다이어그램·오프셋·lag |
| 3. Kafka 신뢰성 | 멱등 키·재시도·DLQ·Outbox | 중복 수신, 소비 후 commit 전 종료, DB commit 후 발행 실패 | 실패 재현과 복구 기록 |
| 4. Redis | 결과 cache-aside·TTL·무효화 | cold/warm 응답, Redis 중지 시 DB fallback, 오래된 값 방지 | 동일 조건 p50/p95·DB 쿼리 수 |
| 5. 검색 | 공개 콘텐츠 mapping·색인·검색, content.published.v1 | text/keyword 차이, 색인 지연, 재색인 후 alias 전환 | 검색 품질 샘플·매핑·재생성 과정 |
| 6. ELK | correlationId·JSON 로그·Kibana 조회 | 하나의 요청을 서비스 간 추적, 실패 로그로 원인 특정 | 개인 정보 없는 로그·대시보드 |
| 7. 운영 실험 | 이미지 빌드·health·CI·장애 복구 | 프로세스/네트워크/저장소 장애와 서비스별 영향 | Dockerfile 선택 이유·runbook |

## 제품에서 먼저 정할 것

기존 운빨을 확인한 뒤 현재 진행 기준을 [백엔드 우선 계획](../01-plan/features/backend-renewal.plan.md)으로 구체화했다. 기존 사주·비장술·카테고리별 좋은 날짜/시간을 우선하며 새 AI·타로 상품을 추가하지 않는다. 기준 데이터·계산 경계 → 회원·프로필 → HTTP 기반 요청/결과 → Kafka·신뢰성 → 열람 정책 → 캐시·검색 순서다. 위 기술별 표는 학습 주제이고 실제 구현 순서는 새 계획을 따른다.

첫 세로 흐름은 API 클라이언트 입력 → `POST /api/v1/fortune-requests` → 202 + requestId → 처리 상태 조회 → 결과 확인이다. 이 엔드포인트들은 아직 없다. 입력 검증·본인 조회·실패·중복 요청을 Swagger·Bruno로 확인한 다음 모바일에 연결한다.

## 단계별 설계 질문

1. 요청의 정본은 왜 PostgreSQL인가? MongoDB의 해석 문서는 무엇의 정본인가?
2. 해석을 HTTP로 동기 호출할 때와 Kafka로 분리할 때, 사용자가 보는 응답은 어떻게 다른가?
3. 메시지를 한 번 소비했다는 것과 결과가 한 번만 저장됐다는 것은 왜 다른가?
4. 캐시가 사라져도 제품이 동작하는가? DB 장애까지 동시에 생기면 어떤 응답이 맞는가?
5. 검색 인덱스를 버리고 재생성할 수 있는가? 검색 누락과 데이터 손실을 어떻게 구분하는가?
6. 컨테이너 재시작·이미지 교체·볼륨 삭제의 데이터 영향은 각각 무엇인가?

## 다른 기술에서 쌓을 경험

- JPA: N+1 재현 → 쿼리 수 확인 → fetch join 또는 조회 전용 DTO 선택. 트랜잭션 경계를 설명한다.
- Querydsl: 조건 조합·페이지네이션 구현. 먼저 Q타입 생성과 PostgreSQL 통합 테스트부터 검증한다.
- Security: Basic은 임시 개발 설정이다. 회원/JWT 또는 세션을 선택하고 본인 요청만 조회 가능한 인가 테스트를 추가한다.
- Gradle: 프로젝트 의존성 그래프·BOM·annotation processor·test와 bootJar 차이를 설명한다.
- React Native/Expo: 요청 중/대기/완료/실패 UI, 재조회 중단 조건, 서버 오류와 입력 오류를 구분한다. 기존 웹은 별도 보존한다.

## 한 작업의 마무리

- 내가 선택한 방식을 코드 없이 2분 안에 설명한다.
- 장애나 경계 상황 하나를 직접 재현한다.
- 예상과 결과가 달랐던 점을 evidence-template에 기록한다.
- 면접 답변은 문제 → 선택 → 대안/비용 → 검증 → 한계 순서로 작성한다.
- 실험하지 않은 부분은 계획이라고 말한다. 초기 세팅을 운영 경험으로 표현하지 않는다.
