# 운빨 백엔드 개발 계획과 요청 가이드

> 2026-11-06 · bkit Plan · 기존 운빨 코드 기반 리뉴얼 설계안. 업무 API·DB는 아직 구현 전이다.

## 핵심 방향

**회원 → 사주 기본정보 → 오늘의 비장술 → 카테고리별 좋은 날짜·시간**을 먼저 완성한다. 이후 비동기 처리·장애 복구·캐시·검색을 붙인다. 앱 화면 작업은 뒤로 둔다.

| 관점 | 결정 |
|---|---|
| 문제 | 기존 기능·데이터 기준 없이 기술부터 붙이면 운빨과 다른 제품이 된다. |
| 해결 | 기존 규칙과 사용자 흐름을 확인하고 작은 기능 단위로 구현·검증한다. |
| 사용자 효과 | 본인 사주와 운세 결과를 안전하게 조회하고 실패 시 다시 확인할 수 있다. |
| 핵심 가치 | 기능 동작뿐 아니라 선택 이유와 실행 근거를 설명할 수 있게 한다. |

## Context Anchor

대상은 기존 운빨 사용자와 백엔드를 학습하는 개발자다. 범위는 명세·논리 설계·개발 순서이며, 핵심 위험은 기준 데이터 부재와 과한 초기 비동기화다. 성공 기준은 기능·API·저장소·검증 순서가 연결되고 기존 확인 사실과 신규 제안이 구분되는 것이다.

## 기존 운빨 기준

기능은 `Luck_BE/main`과 실제 앱 화면·호출이 있는 `luck_FE/dev2`에서 확인했다. FE 기본 브랜치 master는 초기 화면이므로 기능 기준으로 사용하지 않는다. BE dev2의 controller/service/domain 파일들은 main과 동일한 blob임을 대조했다. 기존의 별도 명세·ERD·SQL seed 파일은 확인되지 않아 코드를 바탕으로 재구성했다. 원본 소스·설정·DB 데이터는 복사하지 않는다.

| 유지 | 개선 |
|---|---|
| 사주·비장술 규칙, 카테고리, 좋은 날짜·시간 | 입력 검증과 기준 데이터 버전 관리 |
| 계정·본인 정보·관심 카테고리 | 요청 userId 대신 인증된 사용자로 조회 |
| 추천별·열람 횟수라는 기능 | 재조회·재시도 중복 차감과 동시 요청 방지 |
| 모바일 제품 방향 | 기존 API를 그대로 복제하지 않고 새 계약으로 정리 |

## 개발 순서와 완료 조건

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| 1. 기준 데이터·규칙 | 달력·시주·비장술 조합·해석 자료 확보, 합성 fixture, 순수 계산 함수 | 지원 날짜·윤달·시간 미상·자정/12주기 경계 테스트. 실제 데이터 없으면 데모로 명시 |
| 2. 회원·프로필 | 기본 가입/로그인·토큰 갱신/로그아웃, 사주 입력, 관심 카테고리 | 중복 가입·인증 만료·타인 조회 차단, PostgreSQL 실제 저장 |
| 3. 운세 세로 흐름 | 카테고리, 요청 접수·상태·결과, interpretation HTTP 호출·Mongo 저장 | 접수→결과 조회, 실패·재요청·중복 요청 검증 |
| 4. Kafka·신뢰성 | HTTP 처리 호출을 이벤트로 전환, Outbox·멱등·재시도·DLQ | 커밋/발행 사이 종료·중복 소비·소비자 정지·재시작 실험 |
| 5. 열람 정책 | 추천별·무료 횟수·사용 이력 | 재조회 무료 여부·차감 시점 확정 후 원자적 차감·중복/동시성 테스트 |
| 6. 조회·운영 개선 | Redis → 공개 검색 → 추적 로그·배포 순서 | 캐시 장애 fallback·개인정보 없는 색인·재색인·readiness 확인 |

SMS·소셜 로그인·실제 결제·푸시는 핵심 흐름 이후 진행한다. **기준 데이터 출처·사용 범위, 실제 계산 정확성의 기준, 열람·추천별 정책**은 해당 기능 착수 전에 확정한다. 이름·전화번호·성별 등 기존 필드를 관성적으로 다시 수집하지 않는다.

## 한 기능은 이렇게 진행

`기존 흐름 확인 → Plan → DTO·DB·API Design → 테스트·Do → Check → 필요한 Act`

코드 전에는 흐름·대안·필드 검토표를 짧게 설명한다. 이후 함수 주석·기능 명세·테스트·Swagger·Bruno를 함께 갱신한다. 기능별 상세 계약과 마이그레이션은 착수할 때 확정하고 이 문서의 개요만으로 구현 완료라 하지 않는다.

검증은 `gradlew.bat test bootJar`, 실제 PostgreSQL/Mongo 통합 테스트, 해당 Swagger 호출·Bruno 정상/실패 시나리오다. Docker 설치 후 `docker compose --profile apps --profile elk config --quiet`와 실제 readiness를 확인한다. api-smoke 결과를 실제 DB 검증으로 대체하지 않는다.

## 나에게 시키는 방법

범위·원하는 끝점만 정해 주면 된다. 정한 범위를 매번 다시 승인받지 않고 진행한다.

```text
백엔드 계획 1단계부터 진행해.
Luck_BE/main과 luck_FE/dev2를 참고해서 기존 방식과 개선 이유부터 설명해.
이번에는 기준 데이터 목록·필드 검토·계산 규칙 테스트까지 해줘.
실제 실행 결과와 미검증 항목, 직접 할 실험 1개·면접 질문 2개를 남겨.
```

| 원하는 작업 | 요청 예시 |
|---|---|
| 설계만 | “회원·프로필의 API·DTO·DB만 설계해. 코드는 아직 쓰지 마.” |
| 구현까지 | “확정한 회원·프로필 설계대로 구현하고 DB·Swagger·Bruno 검증까지 해줘.” |
| 이해하며 진행 | “이번 기능의 요청→서비스→DB 흐름과 선택 이유부터 설명하고 작은 단위로 구현해줘.” |
| 이어서 진행 | “백엔드 계획에서 다음 미완료 단계의 첫 기능을 진행해. 완료 조건과 검증 결과를 남겨.” |

## 직접 확인할 것

- 실험: 같은 합성 생일을 양력/음력으로 각각 입력하고 날짜 변환·사주 결과가 어떤 기준으로 달라지는지 대조한다. 아직 미실행이다.
- 면접 질문: 왜 사용자 ID를 요청 본문에서 신뢰하면 안 되는가? DB 커밋 후 메시지 발행 전에 종료되면 무엇을 복구해야 하는가?

이번 작업은 bkit Plan·Design과 문서 Check까지다. 원본 관련 흐름·브랜치 대조, 문서 간 계약·저장소 정합성·링크 검사를 수행했다. 코드·DB 생성과 기능 실행 검증은 아직 진행하지 않았다.
